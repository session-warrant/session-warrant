# bench/serverload/ — 중앙 서버 부하 (k6)

노드가 늘어나면 중앙이 버티는가. 재는 건 두 경로다.

| | 무엇 | 왜 |
|---|---|---|
| 쓰기 `ingest.js` | gRPC `AuditIngestService/Stream` → `audit_event` · `warranted_session` · `unwarranted_session` | 노드 수에 비례해 들어온다. 여기가 막히면 감사 기록이 노드에 쌓인다 |
| 읽기 `read.js` | 대시보드가 부르는 `/api/audit/*` · `/api/nodes` | 쌓인 테이블에서 화면이 뜨는가 |

**둘을 겹쳐 돌리는 게 이 하네스의 요점이다.** 적재가 받은 순번을 직렬화하는
동안 읽기가 같이 느려지는지는 따로 재면 안 보인다.

## 돌리기 — k6 가 직접 돈다

전부 맥에서 돈다. `sudo` 가 필요 없다 — 커널을 건드리지 않는다.

```sh
make check                                      # k6 · 서버 · DB · 인증서
k6 run smoke.js                                 # 길이 뚫렸나 — 30건 보내고 ack 까지 확인

k6 run ingest.js                                # 노드 1대 · 30초 · mTLS
k6 run -e NODES=4 -e DURATION=60 ingest.js
k6 run -e SESSION_EVERY=3 ingest.js             # 세션 이벤트를 촘촘히 — 화면 채우기
k6 run -e PKI= ingest.js                        # 평문 (mtls 프로필 없이 띄운 서버)
k6 run -e PKI= -e ADDR=localhost:9091 ingest.js # t3.micro 컨테이너(dev 프로필)

k6 run -e BASIC=dev@example.com:<암호> read.js   # 읽기 (dev 프로필)
k6 run -e TOKEN="$T" read.js                    # 읽기 (oidc 프로필)
```

각 스크립트가 **시작할 때 어디로 · 어떤 방식으로 붙는지 한 줄 찍고**, 끝에 처리량 ·
ack 지연 · 읽기 지연을 찍는다. 환경 변수는 파일 머리에 있다.

**부하를 걸기 전에 `smoke.js` 를 먼저 돌린다.** health · gRPC 연결 · 스트림 · ack 네 가지를
30건으로 확인하고, 하나라도 어긋나면 0 이 아닌 코드로 끝난다(`thresholds`). 설정이 틀렸을 때
10분짜리 부하를 돌리고 나서 아무것도 안 들어온 걸 아는 일을 막는다. DB 에 30행을 남긴다.

**쓰기의 기본은 mTLS 다**(`PKI=../../.cache/pki`). 제품의 노드 ↔ 중앙이 mTLS 이고
평문은 로컬 개발 전용이라서다. 서버를 `mtls` 없이 띄웠으면 `-e PKI=` 로 비운다.

**서버 프로필과 안 맞으면 10초 안에 멈추고 무엇을 고칠지 찍는다.** 평문으로 TLS 서버에
붙으면 서버가 핸드셰이크 전에 끊어 `error reading server preface: EOF` 가 난다 —
warrantd 에서도 같은 모양이다(`deploy/README.md`). 읽기는 인증을 안 주면 아예 시작하지
않는다. 전건 401 의 지연을 재면 측정이 아니라 거짓이기 때문이다.

### 숫자를 남길 거면 `run.sh`

```sh
./run.sh --nodes 8 --duration 60
./run.sh --scale 1,2,4,8                        # 노드 수만 바꿔 연달아 — 서로 비교 가능
./run.sh --both --nodes 4 --token "$T"          # 쓰기와 읽기를 겹쳐서
./run.sh --read-only --basic dev@example.com:<암호>
make clean-rows CONFIRM=1                       # 가짜 노드가 남긴 행을 지운다
```

`run.sh` 가 k6 보다 더 하는 일은 넷이다 — 사전 조건 확인 · 실행마다 새 epoch ·
쓰기와 읽기 겹치기 · **DB 행수로 처리량 검산**. 결과는 `out/<타임스탬프>/` 에 남고,
종료 코드는 0 통과 · 1 적재가 모자람 · 2 사전 조건 실패다.

**`k6 run` 단독에는 검산이 없다.** 적재가 멱등이라 보낸 것이 전건 중복으로 걸러져도
k6 쪽은 빨랐다고 보고한다. 단독 실행은 epoch 를 제가 뽑으므로 그 함정에 바로 빠지지는
않지만, 「보낸 수」는 어디까지나 상한이다.

## 세션 이벤트를 섞는다

커널 판정만 보내면 **대시보드가 비어 보인다** — Grafana 의 「SSH 접속 현황」은
`ssh_session` 뷰를, 「무영장 세션」은 `unwarranted_session` 을 읽기 때문이다.
그래서 `ingest.js` 는 같은 스트림에 세션 기록을 섞는다(`warrantd` binder 와 같은 모양).

| 변수 | 기본 | |
|---|---|---|
| `SESSION_EVERY` | 20 | 배치 몇 개마다 세션 한 건. 0 이면 안 섞는다 |
| `UNWARRANTED_PCT` | 20 | 세션 중 무영장 비율. 나머지는 영장 세션 |
| `WARRANT_IDS` | — | 세션에 붙일 **서버에 있는** 영장 번호 (`1,2,3`). 대시보드를 볼 거면 이걸 준다 |
| `WARRANT_BASE` | 9500 | `WARRANT_IDS` 가 없을 때 쓰는 가짜 번호. 화면에 `#9500` 으로 보인다 |
| `DENY_PCT` | 3 | 차단 비율. 영장이 감사 모드라 `WOULD_DENY` 로 나간다 |

**대시보드를 볼 거면 서버에 있는 영장 번호를 줘야 한다.** 모르는 번호가 오면 화면이
「페이지가 열린 뒤 발급된 영장인가」 하고 전체를 다시 읽는데, 그때 들고 있던 기록이
최근 한 페이지(5,000건)로 갈린다. 초당 1만 건을 쏘면 매 초 그 일이 일어나 **막대가
계속 사라진다**(2026-11-16). `run.sh` 는 `--token` · `--basic` 이 있으면
`GET /api/warrants` 로 번호를 읽어 넘기고, 없으면 가짜 번호를 쓴다고 찍는다.

**초당 1만 건은 화면이 따라올 수 있는 양이 아니다.** 화면 확인이 목적이면 낮춘다 —
`-e BATCH=5 -e WINDOW=1` 이면 초당 수십 건이다. 실제 노드 한 대는 이 정도를 낸다.

**커널 판정은 영장 세션에만 달린다.** 세션을 열면 그 뒤의 판정이 그 영장 번호 ·
주체 · 정책을 달고 나가고, 다음 세션이 열리면 갈아탄다. 무영장 세션은 기록만 남고
판정을 거느리지 않는다 — 태그가 없으면 `lookup_warrant` 가 비어서 LSM 훅이 아무것도
안 남기고 빠져나가기 때문이다.

**`warrant_id = 0` 인 커널 판정은 만들면 안 된다.** 제품에서 생기지 않는 조합이고,
대시보드도 그런 건 판정 추이에서 뺀다(`src/lib/filters.ts` 의 `if (!c.warranted) continue`).
2026-11-16 에 전건을 0 으로 보냈다가 **표에는 뜨는데 막대그래프만 비어 있는** 상태를
만들었다. 화면이 틀린 게 아니라 데이터가 틀린 것이었다.

**훅과 판정도 섞는다.** 한 칸만 찬 화면은 부하를 봐도 아무것도 안 알려준다.
exec 55 · file_open 25 · unlink 7 · rename 5 · connect 7 · 자기보호 1 의 비율이고,
차단은 `DENY_PCT` 만큼 **훅 전체에 고루** 걸린다 — 훅 고르기와 같은 수로 차단을
정하면 한 훅에만 몰린다(처음에 `seq % 100` 을 둘 다 써서 차단 2,602건이 전건 exec
였다).

- **세션마다 cgroup id 가 새 값이다.** 재사용되지 않는 성질을 지켜야 화면의 「최근 접속」이
  한 줄로 뭉치지 않는다. 2026-11-16 확인: 세션 530건 = 서로 다른 cgroup 530개.
- **무영장 사유를 돌려 쓴다**(`NO_WARRANT` · `NO_KEY` · `KEY_MISMATCH` · `AGENT_UNREACHED`).
  사유가 없으면 서버가 거부한다. `NO_KEY` 는 지문을 비워 보낸다 — 키가 없어서 생긴
  사유에 지문을 실으면 거짓이다.
- **영장 세션은 `warrant_id` 가 0 이면 서버가 거부한다.** 그래서 번호를 꼭 넣는다.
- 계정 4개 · 출발지 · 지문 40개를 돌려 써서 「노드별 · 계정별」 패널이 한 칸으로
  뭉치지 않게 한다.

2026-11-16 확인: `SESSION_EVERY=3` · 노드 2대 · 10초에 세션 530건이 들어가
Grafana 가 **접속 530 · 영장 412 · 무영장 118** 로 읽었다. 훅을 섞은 뒤
`GET /api/audit/events?kind=verdict` 500건에 **영장 없는 판정이 0건**이고
exec · file_open · unlink · rename · connect · 자기보호가 모두 나왔다.

## 인증 — 서버를 어떤 프로필로 띄웠느냐에 달렸다

| 서버 | 쓰기(gRPC 9090) | 읽기(REST 8080) |
|---|---|---|
| 프로필 없음 | `--no-tls` (평문) | `--basic` 도 안 먹는다. 읽기는 못 잰다 |
| `dev` | `--no-tls` | `--basic 계정:암호` |
| `mtls` | 노드마다 인증서 — `make certs NODES=N` | — |
| `oidc` | — | `--token <JWT>` |

`make check` 가 지금 뜬 서버의 모드를 찍어준다.

**mtls 는 노드마다 인증서가 따로 필요하다.** 서버는 `NodeHello` 의 hostname 이
인증서 CN 과 다르면 거부하므로, 가짜 노드 N대를 흉내 내려면 CN 이 다른 인증서가
N개 있어야 한다. `make certs` 가 `deploy/pki/pki.sh` 로 만든다.

## 실측 (2026-11-16, 맥 M-시리즈 · 서버 · PostgreSQL · k6 가 같은 기계)

`audit_event` 에 이미 550만 행이 있는 상태. 배치 100건 · 창 4개 · 15초.
**세션 이벤트를 섞기 전의 측정이다** — 전건이 커널 판정(exec)이었다.

| 노드 | DB 에 들어온 행/s | 노드 1대당 | ack 평균 | ack p95 |
|---:|---:|---:|---:|---:|
| 1 | 14,640 | 14,640 | 24.8ms | 33ms |
| 2 | 15,067 | 7,533 | 50.9ms | 67ms |
| 4 | 14,993 | 3,748 | 104.8ms | 135ms |
| 8 | 15,267 | 1,908 | 208.5ms | 242ms |

**처리량이 노드 수와 무관하게 평평하고, ack 지연만 노드 수에 정비례한다.**
이게 적재가 직렬화된 신호다 — 서버는 받은 순번(`received_seq`, V4)을 advisory
lock 으로 직렬화해 「순번 순서 = 커밋 순서」를 보장한다. 설계대로이고, 그 대가가
이 상한이다. 노드를 늘리면 각 노드가 기다리는 시간이 늘어난다.

**읽기를 겹치면 쓰기가 4배 느려진다** (`--both --nodes 4`, 읽기 5 VU):

| | 혼자 | 읽기와 겹쳐 |
|---|---:|---:|
| 쓰기 처리량 | 14,993/s | **3,720/s** |
| ack 평균 | 104.8ms | **431.0ms** |

그때 읽기 쪽(전건 200):

| 질의 | 평균 | p95 |
|---|---:|---:|
| 처음 화면 `events?limit=1000` | 560.8ms | 768.3ms |
| 이어 받기 `events?after=N` | 40.8ms | 70.4ms |
| 구간 집계 `summary` | 691.8ms | 953.9ms |
| 노드 목록 | 10.2ms | 26.5ms |
| 무영장 세션 | 21.5ms | 47.9ms |

**이어 받기가 처음 화면보다 14배 싸다.** 대시보드가 SSE 알림 뒤 차분만 가져가는
설계(2026-11-09)의 값이 숫자로 나왔다 — 같은 화면을 새로고침으로 떠올리면
매번 560ms 를 낸다.

## t3.micro 로 묶어 재기 (2026-11-16)

`server/compose.yaml` 의 `server` 서비스가 중앙 서버를 **2 vCPU · 1 GiB**(AWS t3.micro)로
묶어 띄운다. 호스트 포트가 8081 · 9091 이라 `bootRun` 과 같이 떠 있을 수 있다.

```sh
cd ../../server && ./gradlew bootJar
docker compose -f compose.yaml --profile t3micro up -d --build
cd ../bench/serverload
./run.sh --nodes 4 --duration 15 --no-tls --addr localhost:9091 --api http://localhost:8081
```

PostgreSQL 에는 제한을 걸지 않는다 — 운영에서 DB 가 RDS 로 빠지는 모양이고, 서버 자체의
한계를 분리해 보려는 것이다.

| 노드 4대 · 15초 | 맥에서 `bootRun` | t3.micro 컨테이너 |
|---|---:|---:|
| DB 에 들어온 행/s | 14,993 | **13,440** |
| ack 평균 | 104.8ms | **117.9ms** |
| ack p95 | 135ms | **207ms** |
| 메모리 | — | 394 MiB / 1 GiB · OOM 0 |

**쓰기만 보면 2 vCPU 로도 거의 안 떨어진다**(-10%). 적재가 advisory lock 으로 직렬화돼
있어서 CPU 가 병목이 아니기 때문이다 — 여기서도 같은 상한이 보인다.

**읽기를 겹치면 무너진다** (`--both --nodes 4`, 읽기 5 VU · 20초):

| | 맥 `bootRun` | t3.micro |
|---|---:|---:|
| 쓰기 처리량 | 3,720/s | **2,185/s** |
| ack 평균 | 431ms | **733ms** |
| 처음 화면 `events` 평균 | 561ms | **3,222ms** |
| 구간 집계 `summary` 평균 | 692ms | **2,021ms** |
| 이어 받기 `after=N` 평균 | 41ms | **488ms** |

**이 읽기 비교에는 교란 요인이 있다 — 인증 방식이 다르다.** 맥 쪽은 Bearer(oidc)이고
컨테이너는 `dev` 프로필의 Basic 이다. Basic 은 쿠키가 없는 k6 가 매 요청 다시 인증해
**요청당 ~75ms**(bcrypt, 유휴 컨테이너 실측)를 낸다. 한 반복에 5~6 요청이므로
반복마다 ~400ms 가 bcrypt 다. 2 vCPU 에서는 그게 CPU 를 먹어 쓰기까지 끌어내린다.
**숫자를 「t3.micro 가 느리다」로만 읽지 말 것** — 인증 비용이 섞여 있다.
`oidc` 는 이 컨테이너에서 발급자 주소가 안 맞아 아직 못 쓴다(`server/README.md`).

### t3.micro 와 같지 않은 것

- **버스트 크레딧이 없다.** t3.micro 의 2 vCPU 는 기준선 10%(≈0.2 vCPU)이고, 크레딧을
  다 쓰면 거기로 떨어진다. Docker 의 `cpus: 2` 는 **크레딧이 무한한 2 vCPU** 다 —
  짧은 측정은 실제보다 후하게 나온다. 몇 분 넘는 부하는 실제 t3.micro 에서 더 나쁘다.
- **CPU 가 다르다.** 실제 t3.micro 는 Intel · AMD x86 이고 여기는 맥의 arm64 다.
- **DB · k6 가 같은 기계에 있다.** 제한은 서버 컨테이너에만 걸리고, PostgreSQL 과 k6 는
  남은 코어를 쓴다. 실제로는 k6 가 밖에 있고 DB 도 따로다.
- **네트워크가 없다.** 같은 기계 안의 루프백이라 지연이 0 에 가깝다.

그래서 이 숫자는 **「2 vCPU · 1 GiB 로 묶으면 이만큼」이지 「t3.micro 에서 이만큼」이
아니다.** 실제 인스턴스에서 재야 하는 값은 따로 남아 있다.

## 함정 — 이것 때문에 하네스가 두 번 틀렸다

- **멱등 때문에 「빠르게 아무것도 안 하는」 측정이 된다.** 적재 키는
  `(node_id, seq_epoch, node_seq)` 다. 같은 `seq_epoch` 로 다시 보내면 서버가
  전건 중복으로 걸러 ack 만 주고, k6 는 빨랐다고 보고한다.
  → `run.sh` 가 실행마다 epoch 를 새로 뽑고, **DB 행수 증가분을 처리량으로 쓴다.**
  k6 가 보낸 건수는 상한으로만 적는다.
- **k6 의 `sleep()` 은 이벤트 루프까지 멈춘다.** 스트림 ack 콜백이 반복이 끝날
  때까지 안 들어와서, 첫 실행은 ack 지연이 전건 40초로 찍혔고 배치도 창 크기(4개)
  만큼만 나갔다. `k6/timers` 의 `setTimeout` 을 `await` 해야 한다
  (`export default async function`).

## 읽을 때

- **처리량은 DB 행수 기준이다.** `보낸 이벤트`는 상한이고, 둘이 어긋나면
  `report.py` 가 실패로 적는다.
- **실행끼리 섞어 비교하지 말 것.** 서버 · DB · k6 가 한 기계에서 CPU 를 다툰다.
  의미 있는 비교는 **한 번의 호출 안에서 노드 수만 바꾼 것**이다 — `./run.sh --scale 1,2,4,8`
  이 그래서 연달아 돈다. (S1 에서 배운 것과 같은 규칙이다.)
- **`audit_event` 는 지금 DEFAULT 파티션 하나뿐이다.** 선언적 파티셔닝은 기술
  스택이 지목했지만 미구현이라, 행이 쌓이면 읽기가 같이 느려진다. 위 읽기 숫자는
  550만 행에서의 값이고, **세션 테이블은 거의 비어 있었다** — 세션을 섞어 다시 재면
  `/api/audit/unwarranted` 와 「SSH 접속 현황」 쪽 숫자가 달라진다.
- **가짜 노드 행은 대시보드 · Grafana 에 섞인다.** 호스트 이름이 `k6-node-*` 라
  눈에 보이고, `make clean-rows CONFIRM=1` 로 지운다. 지우기 전에 건수를 찍는다.
- 이건 **서버 쪽 부하**다. 커널 훅의 비용은 `bench/overhead`(S1), 기록이
  빠짐없이 오는지는 `bench/e2e` 가 본다.

## 왜 별도 저장소가 아닌가

`bench/` 의 다른 하네스와 같은 이유다 — **측정 결과가 리포 안에 있어야 심사
자료가 된다.** 게다가 이 스크립트는 `proto/` 와 `/api/*` 모양에 직접 묶여 있어서,
따로 두면 계약이 바뀔 때 조용히 깨진다. k6 는 단일 JS 파일을 제 바이너리로
돌리므로 `node_modules` 가 없다 — 모노레포에 넣는 비용이 사실상 0이다.

(별도 저장소로 뺀 건 대시보드 `session-warrant-web` 과 `session-warrant-desktop`
뿐이고, 그건 도구 사슬과 담당이 달라서다.)
