Session Warrant · 기술 스택

무엇으로 만들 것인가

범위는 문서 전체, 인원은 2~3명. 이 조합에서 스택 선택의 기준은 성능도 취향도 아니고 막혔을 때 검색으로 풀리는가다. 아래 선택은 전부 그 기준으로 골랐다.

작성 2026-08-19 범위 문서 전체 (Phase 2 포함) 인원 2~3명 에이전트 Go + cilium/ebpf 중앙 Java + Spring Boot

한눈에

  • 커널 — BPF 프로그램은 C로 쓰고 CO-RE로 빌드한다. 커널 버전마다 다시 컴파일하는 방식은 배포판 3종을 검증해야 하는 이 프로젝트에서 감당이 안 된다.
  • 노드 — warrantd는 Go, BPF 로딩과 맵 관리는 cilium/ebpf. PAM 모듈만 C로 따로 뗀다. Go 런타임을 sshd 프로세스 안에 넣을 수는 없다.
  • 중앙 — Java 25 + Spring Boot 4.1. 영장 발급·승인·감사 조회가 전부 여기 있고, 백엔드 담당자의 실질적 결과물이 이 모듈이다.
  • 계약 — proto/를 가장 먼저 확정한다. 이게 있어야 커널 담당과 서버 담당이 서로를 기다리지 않는다.
  • 검증 — 벤치마크와 우회 시도 테스트를 처음부터 리포지토리에 넣는다. 이 둘이 논문의 표와 그래프가 된다.

03

커널 계층 — C, 그리고 CO-RE

여기서 유일하게 고민할 것은 언어가 아니라 빌드 방식이다. BCC처럼 노드에서 런타임에 컴파일할 것인가, CO-RE로 한 번 빌드해 어디서나 돌릴 것인가.

CO-RE로 간다. BCC 방식은 노드마다 clang과 커널 헤더를 깔아야 하는데, 배포판 3종을 검증해야 하는 이 프로젝트에서는 그 자체가 실험 변수가 된다. CO-RE는 vmlinux.h와 BTF 재배치로 커널 구조체 오프셋 차이를 실행 시점에 흡수하므로, Ubuntu 24.04에서 빌드한 .o 하나가 26.04와 Rocky 9에서도 그대로 로드된다. 논문의 “배포판 호환성” 절이 여기서 나온다.

# vmlinux.h 생성 — 개발 VM에서 한 번, 리포지토리에 커밋하지 않는다
bpftool btf dump file /sys/kernel/btf/vmlinux format c > bpf/vmlinux.h

# 빌드
clang -O2 -g -target bpf -D__TARGET_ARCH_x86 \
      -c bpf/warrant.bpf.c -o bpf/warrant.bpf.o

붙일 훅 목록

문서 전체 범위이므로 훅이 스무 개를 넘는다. 한 번에 다 붙이지 말고 아래 순서로 하나씩 늘린다. 훅 하나를 붙일 때마다 verifier 통과와 오버헤드를 같이 확인하는 것이 유일하게 안전한 진행 방식이다.

순서훅역할난이도

2lsm/bprm_check_securityexec 화이트리스트. inode 기반 판정의 첫 사례낮음

원 문서 §15의 “감사와 강제가 같은 코드를 쓴다”를 실현하려면 판정 로직이 static __always_inline 함수 하나로 떨어져야 하고, LSM 훅과 kprobe가 그 함수를 각자 호출하는 형태여야 한다. 이 구조는 C에서는 자연스럽지만 Rust(aya)에서는 매크로 경계 때문에 까다롭다. BPF 쪽을 C로 두는 실질적인 이유 중 하나다.

04

노드 에이전트 — Go가 맡는 일곱 가지

warrantd는 “BPF를 올리는 프로그램”이 아니다. 실제로는 이 프로젝트에서 코드가 가장 많이 쌓이는 모듈이고, BPF 로딩은 그중 한 조각일 뿐이다.

책임라이브러리메모
BPF 로딩 · 맵 관리cilium/ebpf + bpf2gobpf2go가 .o를 Go 바이트 배열과 타입 안전한 구조체로 생성한다. go generate 한 번으로 커널 구조체와 Go 구조체의 어긋남이 컴파일 오류로 잡힌다
훅 attach · pinebpf/linklink.AttachLSM, link.AttachTracing. 링크와 맵을 /sys/fs/bpf에 pin해야 warrantd 재시작 중에도 강제가 유지된다
감사 이벤트 소비ebpf/ringbuf별도 고루틴에서 논블로킹 소비. 유실 구간을 명시적으로 기록해야 한다는 §14 요구가 여기 구현된다
중앙 통신grpc-go + protobuf영장 push는 서버 스트리밍, 감사 이벤트는 클라이언트 스트리밍. 단절 시 재연결은 grpc.WithConnectParams의 백오프에 맡긴다
영장 로컬 캐시bbolt중앙 단절 시에도 캐시된 영장으로 계속 집행해야 한다(§17). 파일 하나짜리 임베디드 KV라 배포가 늘지 않는다
inode 자동 갱신golang.org/x/sys/unixfanotify로 허용 바이너리 경로를 감시하다가 교체되면 맵을 다시 쓴다. 패키지 업데이트로 규칙이 조용히 깨지는 것을 막는다
위임 승계 (Phase 2)godbus/dbus/v5systemd의 JobNew·UnitNew 구독. docker.sock 쪽은 SO_PEERCRED로 피어 pid를 읽어 태그를 확인한다

왜 Rust가 아니라 Go인가

기술적으로는 aya도 충분히 된다. 결정적인 차이는 막혔을 때 나오는 검색 결과의 양이다. Cilium, Tetragon, Falco, Parca가 전부 cilium/ebpf 계열이라 verifier 오류 메시지 하나를 붙여 넣으면 대개 같은 문제를 겪은 이슈가 나온다. 학부 일정에서 이 차이는 취향 문제가 아니라 일정 리스크다. 위 표의 일곱 가지 중 BPF와 직접 관련된 것은 셋뿐이고 나머지 넷은 평범한 서버 코드라는 점도 Go에 유리하게 작용한다.

systemd 유닛에서 반드시 지킬 것

# /etc/systemd/system/warrantd.service
[Unit]
Before=sshd.service          이게 없으면 부팅 직후 세션이 태그 없이 시작된다
After=network-online.target

[Service]
Type=notify
ExecStart=/usr/local/bin/warrantd
Restart=always
AmbientCapabilities=CAP_BPF CAP_PERFMON CAP_SYS_ADMIN
LimitMEMLOCK=infinity        구커널 대비. 5.11+에서는 불필요하지만 남겨 둔다
05

PAM 모듈 — 여기만 C를 다시 쓴다

언어를 넷으로 늘리는 유일한 이유가 이 모듈이다. 그리고 그럴 만한 이유가 있다.

PAM 모듈은 sshd 프로세스 주소 공간에 dlopen으로 적재된다. Go로 c-shared 빌드를 하면 sshd 안에서 Go 런타임과 그 스레드들이 뜬다. 인증 경로에서 이건 받아들일 수 없는 위험이고, 실제로 fork 안전성 문제도 있다. 그래서 이 모듈만 C로 얇게 쓴다.

대신 모듈 자체는 최대한 멍청하게 만든다. 정책 판단이나 서명 검증을 여기서 하지 않고, 유닉스 소켓으로 warrantd에 물어보고 답만 받는다. 코드가 200줄을 넘어가면 설계가 잘못된 것이다.

PAM 모듈이 하는 일

  • account 단계 — 유효한 영장이 있는지 warrantd에 질의
  • session 단계 — XDG_SESSION_ID를 읽어 warrantd에 전달
  • 타임아웃 — 응답이 없으면 통과시킨다(§17의 fail-open)

PAM 모듈이 하지 않는 일

  • cgroup id 조회 — warrantd가 XDG_SESSION_ID로 직접 찾는다
  • 맵 쓰기 — BPF 접근은 전부 warrantd 쪽에 둔다
  • 서명 검증 — 인증 경로에 암호 연산을 넣지 않는다
PAM 스택 순서가 곧 버그의 근원이다

pam_warrant.so는 pam_systemd.so보다 뒤에 놓여야 한다. 그 전에는 session-N.scope가 아직 만들어지지 않아 cgroup id를 읽을 수 없다. 원 문서 §09가 “선행 검증이 필요한 세 가지” 중 하나로 이 타이밍을 꼽은 이유이고, PoC 첫 주에 이것부터 확인해야 한다. /etc/pam.d/sshd를 잘못 건드리면 SSH 로그인이 통째로 막히므로, VM 콘솔 접근 경로를 반드시 확보해 두고 작업한다.

06

중앙 서버 — Java + Spring Boot 4.1

백엔드 담당자의 실질적 결과물이 이 모듈이다. 그래서 “돌아가면 됨”이 아니라 면접에서 설명할 수 있는 구조로 짜는 것이 목표다.

관심사선택이유
웹 계층Spring Web MVC + 가상 스레드WebFlux는 이 프로젝트에 필요 없다. Java 25 가상 스레드로 동시성 요구는 충분히 해결된다
에이전트 통신spring-boot-starter-grpc-server영장 push는 서버 스트리밍이 자연스럽다. REST 폴링으로 하면 “즉시 발효”라는 제품 주장이 약해진다
인증 · 인가Spring Security + OIDC조직 신원 매핑이 제품 핵심이므로 자체 회원가입을 만들지 말고 OIDC 공급자(Keycloak)를 붙인다. sub가 그대로 subject_id가 된다
영장 서명JDK 내장 Ed25519JDK 15부터 KeyPairGenerator.getInstance("Ed25519")가 표준이다. BouncyCastle을 넣을 이유가 없다
직렬화protobuf 바이트에 서명JSON에 서명하면 안 된다. 키 순서와 공백 때문에 정규화 문제가 생긴다. protobuf 직렬화 결과에 서명하고 그 바이트를 그대로 전송한다
영속화Spring Data JPA + Flyway영장 계보(발급 → 연장 → 만료)는 이벤트 소싱까지 갈 필요 없이 append-only 테이블로 충분하다. 스키마 이력은 Flyway로 남긴다
테스트Testcontainers + JUnit 5 + AssertJPostgreSQL을 컨테이너로 띄워 통합 테스트를 돌린다. 심사에서 “테스트는요?”에 답이 된다

도메인 모델은 문서 §12를 그대로 옮긴다

커널 구조체와 서버 엔티티가 어긋나면 그 순간부터 디버깅이 지옥이 된다. struct warrant의 필드를 그대로 protobuf 메시지로 옮기고, 서버 엔티티와 BPF 맵 값이 같은 .proto에서 생성되게 한다. 이것이 proto/를 가장 먼저 확정하라는 §15의 이유다.

이 모듈에서 나오는 면접 소재

짧은 유효기간과 싼 갱신, revoked 한 바이트로 끝나는 즉시 취소, 정책 결정(중앙)과 집행(커널)의 분리. 이 셋은 각각 액세스 토큰 수명 설계, JWT 폐기 문제, PDP/PEP 분리라는 백엔드 표준 주제와 정확히 같은 구조다. 구현하면서 이 대응 관계를 의식적으로 정리해 두면 그대로 이력서 한 줄이 된다.

07

데이터 계층 — PostgreSQL 하나로 시작한다

감사 이벤트가 많이 쌓인다는 이유로 처음부터 ClickHouse를 넣고 싶어지지만, 2~3인 팀에서 저장소를 둘로 나누는 비용은 생각보다 크다.

데이터저장소설계
영장 · 정책 · 승인 계보PostgreSQL 18건수가 적고 트랜잭션이 중요하다. 계보는 append-only, 현재 상태는 뷰로 계산
감사 이벤트PostgreSQL 선언적 파티셔닝일 단위 range 파티션 + BRIN 인덱스. 데모 규모(노드 3~5대, 2주)에서는 이걸로 충분하다
리포트 · 대시보드Grafana“영장 없는 접속 현황”은 Grafana 대시보드 한 장으로 끝난다. 프론트를 직접 만드는 것보다 훨씬 빠르다
이벤트 볼륨 실험 (선택)ClickHouse부하 실험까지 논문에 넣고 싶을 때만. 같은 스키마를 양쪽에 넣고 비교 자체를 결과물로 삼으면 추가 작업이 낭비가 아니게 된다

메시지 큐는 넣지 않는다. gRPC 클라이언트 스트리밍에 백프레셔가 이미 있고, 중앙이 잠깐 죽어도 warrantd의 로컬 버퍼가 받아 준다. Kafka를 넣는 순간 운영 대상이 하나 늘고 심사에서는 “왜 필요했나요”를 답해야 한다.

Part III개발과 검증
08

개발 환경 — VM이 곧 실험 장비다

이 프로젝트에서 개발 환경은 편의 문제가 아니라 실험의 재현성 문제다. 발표 당일 커널이 다르면 그날로 끝난다.

기준 환경

Ubuntu 24.04 LTS · 커널 6.8

일상 개발과 데모의 기준으로 삼는다. BPF LSM은 lsm= 부트 파라미터로 활성화하고, 그 절차 자체를 deploy/enable-bpf-lsm.sh로 스크립트화해 커밋한다. 팀원이 “내 VM에서는 안 되는데요”를 말할 여지를 없앤다.

호환성 검증

Ubuntu 26.04 LTS · 커널 7.0 / Rocky Linux 9

CO-RE가 실제로 동작하는지 확인하는 대상이다. 같은 .o를 재컴파일 없이 로드해 통과하면 그것이 논문의 호환성 표가 된다. RHEL 계열을 하나 넣는 이유는 원 문서 §19가 지적한 “Teleport가 후퇴한 이유”와 정면으로 맞닿아 있기 때문이다.

프로비저닝

Vagrant + libvirt, Ansible

Vagrantfile과 플레이북을 리포지토리에 넣어 vagrant up 한 번으로 3노드 환경이 서게 만든다. 스냅샷을 찍어 두면 커널 패닉이 나도 30초면 복구된다. PAM을 건드리는 프로젝트에서 스냅샷은 선택이 아니다.

CI

GitHub Actions

일반 러너에서는 BPF를 로드할 수 없으므로, CI에서는 빌드와 verifier 통과 여부까지만 본다. Go 테스트, Java 테스트, clang 빌드, bpf2go 생성물이 최신인지 확인하는 정도면 충분하다. 실제 로드 검증은 QEMU 기반 vmtest를 붙이거나, 야간에 개인 VM에서 돌리는 스크립트로 대체한다.

09

검증 하네스 — 논문의 표는 여기서 나온다

벤치마크와 우회 시도 테스트를 나중에 붙이려 하면 안 붙는다. 리포지토리 초기 구조에 bench/를 넣고 시작한다.

오버헤드 측정

측정 대상은 “훅이 붙었을 때 얼마나 느려지는가”이고, 비교군은 최소 셋이다. 훅 없음 / 훅 있고 영장 없음 / 훅 있고 영장 있음. 원 문서 §13의 핵심 주장인 “영장 없는 프로세스는 조회 한 번으로 빠져나간다”가 참인지 아닌지가 가운데 항목에서 판가름 난다.

층위도구측정하는 것
마이크로자체 Go 벤치 · hyperfineopenat·execve·connect 단일 syscall 지연. 훅당 나노초 단위 비용
서브시스템fio · sysbench파일 IO 처리량. file_open 훅의 실제 영향이 여기서 드러난다
애플리케이션nginx + wrk · make -j현실 워크로드에서의 체감 차이. “실무에 넣어도 되는가”에 대한 답
훅 자체bpftool prog profile프로그램별 실행 횟수와 사이클. 어느 훅이 비싼지 직접 짚어 준다

우회 시도 테스트

원 문서 §04의 표가 그대로 테스트 케이스다. 표의 각 행을 bats 케이스 하나로 옮기면, 그 표는 주장이 아니라 실행 가능한 증거가 된다. 심사에서 가장 강한 카드가 이것이다.

# bench/bypass/tag_propagation.bats
@test "sudo를 거쳐도 태그가 유지된다" {
  run_in_warrant_session 'sudo id -u'
  assert_tagged $(last_pid)
}

@test "nohup으로 분리해도 태그가 유지된다" {
  run_in_warrant_session 'nohup sleep 300 &'
  assert_tagged $(pgrep -n sleep)
}

@test "systemd-run --scope는 2차 방어선에 걸린다" {
  run_in_warrant_session 'systemd-run --scope sleep 300'
  assert_tagged $(pgrep -n sleep)      cgroup은 바뀌지만 fork 체인이 살아 있다
}

@test "실행 화이트리스트에 없는 systemctl은 exec에서 막힌다" {
  run_in_warrant_session 'systemctl status sshd'
  assert_denied                        §04의 3중 방어 중 첫 겹
}
실패하는 테스트도 커밋한다

원 문서 §18이 인정한 네 가지 구멍(만료 전 열어둔 fd, connect 없는 UDP, 데몬 위임, kubectl exec)에 대해서도 테스트를 쓰고 skip 사유를 명시해 커밋한다. “알고 있으나 막지 못한다”와 “모른다”는 심사에서 완전히 다르게 취급되고, 이 차이를 코드로 증명하는 방법이 이것이다.

Part IV팀
10

리포지토리 구조와 역할 분담

모노레포로 간다. 계층이 다섯이라도 세 사람이 같은 히스토리를 보는 편이 낫고, proto/ 변경이 양쪽에 동시에 반영되어야 하기 때문이다.

session-warrant/
├── proto/       protobuf 스키마 — 팀 간 계약. 여기부터 확정한다
├── bpf/          C · BPF 프로그램, vmlinux.h는 gitignore
├── agent/        Go · warrantd, bpf2go 생성물 포함
├── pam/          C · pam_warrant.so (200줄 이내)
├── server/       Java · Spring Boot
├── web/          대시보드 — Grafana로 대체 가능
├── deploy/       Vagrantfile · Ansible · systemd unit · grub 스크립트
└── bench/        오버헤드 벤치 · 우회 시도 테스트
담당모듈주 언어첫 2주 과제
A · 커널 bpf/ · agent/ · pam/ C, Go file_open 훅 오버헤드 실측. 이 숫자가 안 나오면 강제 모드 설계 전체를 다시 잡아야 한다
B · 서버 proto/ · server/ Java .proto 초안 확정과 영장 발급·서명 경로. A가 기다리지 않게 스키마를 먼저 낸다
C · 검증·운영 deploy/ · bench/ · web/ Shell, TS 3노드 Vagrant 환경과 bats 하네스 골격. A의 첫 훅이 나오는 즉시 돌릴 수 있게 준비

2명이라면 C를 없애고 deploy/는 A가, bench/는 B가 가져간다. 벤치마크를 커널 담당이 아닌 사람이 짜는 편이 오히려 낫다. 만든 사람이 자기 코드를 측정하면 유리한 조건만 재게 되기 때문이다.

병렬화의 조건은 딱 하나다

첫 주에 proto/warrant.proto를 확정하는 것. 여기에 struct warrant의 모든 필드와 정책 표현이 들어가고, 그 순간부터 A는 맵 판정을, B는 발급 API를, C는 테스트 픽스처를 각자 만들 수 있다. 이 파일이 늦어지면 세 사람이 서로를 기다리는 구간이 생기고, 학부 일정에서 그 2주는 회복이 안 된다.

11

이 스택으로도 남는 위험

범위를 문서 전체로 잡았으므로, 스택 선택으로 줄일 수 있는 위험과 그렇지 않은 위험을 갈라 둔다.

스택으로 줄인 위험

  • 배포판별 재컴파일 — CO-RE로 흡수
  • 구조체 어긋남 — bpf2go 생성물이 컴파일 타임에 잡는다
  • 검색으로 안 풀리는 문제 — cilium/ebpf 생태계 규모로 완화
  • 서명 정규화 버그 — protobuf 바이트 서명으로 회피
  • 환경 재현성 — Vagrant + 스냅샷

스택으로 못 줄이는 위험

  • verifier와의 싸움 — 훅을 하나씩 늘리는 규율로만 관리된다
  • file_open 오버헤드 — 측정 결과가 나쁘면 설계 변경
  • 훅 20개 이상의 절대량 — 범위를 문서 전체로 잡은 대가
  • PAM 실수로 인한 로그인 차단 — 콘솔 접근 경로 확보로만 대응
  • D-Bus 승계의 레이스 — 원 문서도 100%가 아니라고 인정한 부분
범위에 대한 솔직한 한 마디

문서 전체를 선택하셨으므로 그에 맞춰 짰지만, 위 표의 오른쪽 열은 스택을 어떻게 고르든 남는다. §03의 훅 순서 1~4까지가 4주 안에 끝나지 않으면, 그 시점에 5~7을 설계로 돌리는 결정을 내려야 한다. 그 판단 시점을 미리 일정에 박아 두는 것이 범위를 넓게 잡은 프로젝트에서 유일하게 효과적인 안전장치다.
