# 실험 기록 (S0 · S1 · S2)

스파이크에서 실제로 측정한 것과, 측정하다가 발견한 하네스 결함을 시간순으로 남긴다.
**결론만이 아니라 틀렸던 중간 결론과 그걸 어떻게 알아냈는지를 같이 적는다** — 논문의
「검증 방법」 절이 여기서 나온다.

기획서 §09가 지목한 선행 검증 셋: PAM에서 session scope가 확정되는 타이밍(S3) ·
`file_open` 훅의 실측 오버헤드(S1) · inode 갱신 추적의 안정성(S4).
이 중 **둘째가 가장 위험하므로 거기서 시작했다.**

| | 스파이크 | 판정 기준 | 상태 |
|---|---|---|---|
| S0 | 환경 · 빈도 프로파일 | attach·동작 확인 | ✅ |
| S1 | `file_open` 오버헤드 | 한 자릿수 % | ✅ **통과 (1% 미만)** |
| S2 | 태그 두 겹 — §04 표 | 앞 3줄 초록, 뒤 4줄 '끊김' | ✅ |
| S3 | PAM 타이밍 | `present_t0` 전건 yes | ✅ **통과 (11/11, 공백 0)** |
| S4 | inode 안정성 | 재컴파일 지점 목록화 | 미착수 |

측정 환경은 전 구간 같은 기계다 — Ubuntu 24.04.4 / 커널 6.8.0-138-generic
(S1 4차부터 -139) / i7-1165G7 8코어 물리 서브 PC. VM이 아니다(BPF LSM은
부팅 파라미터와 커널 BTF에 묶여 있어서, 가상화 층을 끼우면 "안 되는 게 커널 문제인지 가상화 문제인지"를
매번 의심하게 된다).

## S0 — 환경과 빈도 프로파일

**질문:** BPF LSM이 이 커널에 붙는가. 그리고 `file_open` 은 초당 몇 번 불리는가.

`bpf/smoke.bpf.c` 로 다섯 훅을 붙여 세기만 했다. 유휴 상태 개발 노트북에서 71초.

### 결과

| 측정 항목 | 값 | 의미 |
|---|---|---|
| `file_open` 빈도 | 유휴 초당 5~15, 버스트 400~1,200 | **사전 추정(초당 수천)보다 두 자릿수 낮다** |
| 쓰기 의도 비중 | **4.7%** (123 / 2,598) | 앞문 하나가 95%를 거른다 |
| `sched_process_fork` | 71초에 51건 | 2차 방어선은 사실상 공짜 |
| `dev` major | 0(procfs·sysfs·tmpfs) 우세 | 실디스크는 소수 |
| cgroup id | 세션·서비스마다 다름 (systemd 자신은 pid=1) | §04의 1차 태그가 실물로 성립 |

### 얻은 것

1. **`f_mode & FMODE_WRITE` 비트 테스트 하나가 판정 함수의 앞문이어야 한다.**
   훅은 100% 불리지만 맵 조회까지 가는 건 5%다. 이 한 줄이 S1의 설계를
   3단이 아니라 4단으로 바꿨다.
2. **superblock 필터로 건너뛰지 않는다.** major 0 이 트래픽 대부분이지만
   `/proc/sys/kernel/*` 쓰기와 `/sys/fs/cgroup` 조작은 정확히 통제 대상이다.
   쓰기 게이트 하나로 충분하다 (§15).

### 한계

**유휴 노트북 숫자다.** 그래서 S1은 반드시 부하 구간에서 재기로 했다.
S1에서 실제로 정반대 프로파일(major 259가 98~99%)이 나왔고, **둘 다 참이다** —
dev major 분포는 워크로드의 성질이지 훅의 성질이 아니다.

## S1 — `file_open` 훅 오버헤드

**질문:** 파일 열기마다 LSM 훅을 붙이면 서버가 얼마나 느려지는가.
**실패하면:** 쓰기 통제를 `inode_{create,unlink,rename,link,symlink}` 5종만으로
재설계해야 하고, 그 위에 얹을 정책 모델·감사 스키마가 전부 흔들린다.

### 설계 — 왜 3단이 아니라 5티어인가

S0에서 쓰기 비중이 4.7%로 나왔으므로 쓰기 게이트가 **독립된 측정 층**이 된다.
3단으로 재면 "훅이 비싼가 판정이 비싼가"가 뭉개진다.

| | 훅 내용 | 재는 것 |
|---|---|---|
| A | 훅 없음 | 기준선 |
| B | `return 0` 만 | LSM 훅 부착 자체의 비용 |
| C | `+ f_mode & FMODE_WRITE` 앞문 | 95%가 여기서 끝난다 |
| E | D와 **같은 프로그램**, 영장 없음 | 조회 1회로 빠져나가는가 |
| D | `+ cgroup 조회 · 맵 2회 · 시간 비교` | 나머지 5%가 내는 비용 |

**티어는 파일이 아니라 컴파일 타임 상수다** (`gate.bpf.c`, `-DTIER=`).
C는 B에 한 줄 더한 것이고 D는 C에 조회를 더한 것이라는 관계가 소스에 그대로
보여야 한다. 파일 넷으로 쪼개면 티어끼리 슬금슬금 달라져도 아무도 모른다.

**E는 새 프로그램이 아니라 `gate_d.bpf.o` 를 태그 없이 돌린 것이다.**
프로그램이 같아야 "영장 유무" 하나만 분리된다. 기술스택 문서 §검증하네스가
요구하는 비교군 셋(훅 없음 / 훅 있고 영장 없음 / 훅 있고 영장 있음)이 A·E·D다.

### 설계 — 매크로와 마이크로를 나눈 이유

**평균이 아니라 p99를 본다.** 평균 2%인데 p99가 30%면 못 쓴다. 그런데 hyperfine
반복은 수십 회라 거기서 p99를 뽑는 건 의미가 없다. 그래서 두 종류를 따로 뽑는다.

| | 무엇 | 어떻게 | 빌드 |
|---|---|---|---|
| 매크로 | 워크로드 벽시계, A 대비 % | hyperfine, 티어 교차 | `PROBE=0` |
| 마이크로 | 훅 1회당 ns 분포, p99 | BPF 안의 log2 히스토그램 | `PROBE=1` |

### 워크로드 — 부하 구간이어야 한다

픽스처는 네트워크를 타지 않는다(`fixture.sh`). 재현 가능해야 한다.

| | 하는 일 | 열기 | 쓰기 비중 | 이 워크로드가 답하는 질문 |
|---|---|---|---|---|
| `w_untar` | 파일 2만 개 tar 풀기 | 40,851 | **98.6%** | **앞문이 못 막을 때 얼마나 비싼가** |
| `w_find` | `/usr` 전체 훑으며 1바이트 읽기 | 168,882 | 0.0% | 앞문이 실제로 막는가 |
| `w_build` | `.c` 400개 8병렬 컴파일 | 46,778 | 2.6% | 현실 서버 작업에서 체감되나 |
| `w_git` | 2만 파일 리포 `git status` ×20 | 4,639 | 1.1% | 짧고 잦은 명령에서는 |

`w_untar` 와 `w_find` 가 양 극단이고 실제 서버는 그 사이 어딘가다.
S0의 유휴 쓰기 비중 4.7%로 보면 현실은 `w_build`(2.6%) 쪽에 가깝다.

### 1차 실행 (2026-08-31, `out/` 미보존) — 하네스 결함 3건

숫자를 얻기 전에 하네스가 틀렸다는 걸 먼저 알았다.

**결함 1 — 계측이 판정 안에 있었다.**
`oh_bump()` 를 판정 함수 안에 뒀더니 티어마다 계측 횟수가 달랐다(B 0회, C 1회,
D 2회). B→C 점프가 앞문 비용이 아니라 **계측 비용**이 되어버렸다.
→ 판정은 결과 코드만 돌려주고, 세는 건 전부 타이머를 닫은 뒤에 한다.

**결함 2 — 구조적 0 이 측정된 0 처럼 보였다.**
쓰기 비중을 판정 경로에서 뽑았더니 티어 B가 `0 (0.0%)` 로 찍혔다. B에는 그
코드가 아예 없어서 나온 0인데 표에 나란히 놓으면 "측정해서 0"과 구별되지 않는다.
→ 쓰기 비중을 `dev` 히스토그램에서 뽑는다.

**결함 3 — dev major가 255에서 잘렸다.**
"major 255 = 98.9%" 라는 값을 보고했는데 실제로는 **259**(nvme/blkext)였다.
맵이 512엔트리라 클램프에 걸린 것이다. → 8192엔트리로 늘리고 4095에서 클램프.

추가로 `PROBE=0` 에서 판정 결과를 아무도 안 쓰면 clang이 판정 자체를 지워버려
티어 C·D가 B와 같아질 수 있다는 걸 발견했다 → `asm volatile` 배리어를 넣었다.

**그리고 매크로에 분해능이 없었다.** 티어를 A블록→B블록→C블록으로 몰아 돌려서
그 시간 동안의 드리프트가 통째로 티어에 얹혔다 — `w_find` 에서 B·C·D가 A보다
빠르게(-3.4%, 유의) 나왔다. → `--passes` 교차 실행과 `판정` 열을 넣었다.

### 발견 1 — §13의 비용 주장은 거짓이다 (E ≈ D)

기획서 §13: *"영장 없는 프로세스는 조회 한 번으로 빠져나간다."*

**빠져나가는 건 맞다** — E의 `tag_hit=0 tag_miss=40,239`, 첫 조회에서 정확히 끝난다.
**그런데 싸지 않다.** `w_untar` 에서 E가 D 비용의 **92%** 를 낸다(71 / 77ns).

비용은 두 번째 조회가 아니라 **거기까지 가는 데** 있다:

```
[쓰기 확인]  →  [cgroup id + 1차 조회]  →  [2차 조회 + 만료 비교]
   21ns             +51ns   ← 90%              +6ns
```

`bpf_get_current_cgroup_id()` 는 `task → cgroups → dfl_cgrp → kn → id` 를 타야 한다.
**영장이 있든 없든 거기까진 똑같이 간다. 답이 "없음"이라고 질문 비용이 줄지 않는다.**

**영향:** "실서버는 무영장 세션이 대다수라 더 쌀 것"이라는 논거를 쓸 수 없다.
오버헤드는 최악값(D)으로 잡는다. 방향이 보수적이라 기존 추정치가 나빠지지는
않지만, **그 문장은 논문·발표에서 빼야 한다.**

꼬리에서는 D가 더 비싸다(`w_untar` p99.9 E 128-255 vs D 256-511;
`w_build` p99 E 256-511 vs D 512-1023). 두 번째 조회 비용은 p50이 아니라
tail에만 나타난다.

### 발견 2 — 2차의 "+2.0%"는 물리적으로 불가능한 값이었다

마이크로로 검산하면:

```
+2.0% of 1.090s = 22ms  ÷ 40,851 calls = 539 ns/call
2차 실행의 커널 안 실측 D 판정 비용        = 177 ns/call
                                          ↑ 3.0배 차이
```

훅이 실제로 쓴 시간을 다 더해도 7.2ms인데 스톱워치는 22ms 느려졌다고 말했다.
나머지 15ms는 훅이 한 일이 아니다.

**주의 — 실행을 섞어 비교하지 말 것.** 처음에 3차의 77ns 와 대조해 "7배"라고
적었는데 틀렸다. 2차는 기계가 베이스 클럭이라 훅 자체가 177ns 로 느렸다.
매크로 Δ 는 반드시 **같은 실행의** 마이크로와 대조한다 — `report.py` 의 검산
절이 실행 디렉터리 안에서만 짝을 짓는 이유다.

**진짜 값:**

```
77ns × 40,851 = 3.16ms  →  A(875ms) 대비 0.36%
LSM 부착 비용(간접호출)을 얹어도  ≈ 0.4~0.5%
```

워크로드별 마이크로 유도 예상 Δ:

| 워크로드 | 열기 | net ns | 총비용 | A 대비 |
|---|---|---|---|---|
| `w_untar` | 40,851 | 77 | 3.16ms | **0.36%** |
| `w_find` | 168,881 | 6 | 1.00ms | 0.16% |
| `w_build` | 46,778 | 40 | 1.87ms | 0.07% |
| `w_git` | 4,639 | 17 | 0.08ms | 0.03% |

**전부 매크로 노이즈 바닥보다 한 자릿수 아래다** — `w_untar` 는 ±0.93%,
`w_find` 는 ±5.99%, `w_build` 는 ±10.04%. 2차의 +2.0%도 3차의 -0.5%도
둘 다 훅을 잰 값이 아니다. 2차 실행 기준으로도 예상 Δ 는 0.66% 였다 —
**클럭 상태에 따라 0.4~0.7%, 어느 쪽이든 1% 미만이다.**

0.4%를 매크로로 유의하게 잡으려면 sd 4%에서 n≈900 런이 필요하다.
**재실행으로 해결할 문제가 아니다 — 저울을 바꿔야 한다.**

| | |
|---|---|
| 판정 | **통과.** 기준은 "한 자릿수 %" 였고 실제는 **1% 미만** |
| 1차 근거 | **마이크로** — 최악 조건 훅 1회당 77ns × 호출수 = **~0.5%** |
| 2차 근거 | 매크로는 **상한**으로만 — "±1.5% 안에서 분해되지 않음" |
| 철회 | ~~"+2.0% 최악조건"~~ — 물리적으로 불가능한 값 |
| 철회 | ~~"무영장 세션이 많으면 싸다"~~ — E≈D로 반증 |
| 유지 | **앞문 설계** — `w_find` 에서 C·E·D 전부 동일(6~12ns) |

**방법론적 결론:** µs 이하 훅의 비용은 벽시계로 재는 것이 아니다. 커널 안에서
1회 비용을 재고 호출수를 곱한다. 매크로는 그 계산이 현실과 자릿수로 어긋나지
않는지 확인하는 용도로만 남는다. 이번엔 어긋났고(2% vs 0.4%), 그래서 매크로 쪽이
틀렸다는 걸 알았다.

이 검산은 `report.py` 의 **「검산: 마이크로 → 매크로」** 절로 자동화했다.
사람이 매번 눈치채야 하는 상태로 두지 않는다. 과거 두 실행에 소급 적용하면:

| 실행 | 워크로드 | 예상 Δ | 실측 Δ | 배 | 판정 |
|---|---|---|---|---|---|
| 2차 | `w_untar` D | +0.66% | **+2.0%** | 3.0x | ⚠ 훅이 낼 수 없는 값 |
| 2차 | `w_build` D | +0.11% | **-35.7%** | 320x | ⚠ 훅이 낼 수 없는 값 |
| 3차 | `w_untar` D | +0.36% | -0.5% | 1.5x | 노이즈 이하 |

**헤드라인으로 쓰던 값과 이미 인공물로 판정했던 값이 같은 규칙에 걸린다.**
그 둘을 구별하려면 사람이 매번 마이크로를 뒤져 곱해봐야 했다.

### 남은 것

### 4차 실행 (2026-09-22, `out/20260922-232054`) — 읽기 감시 티어 R · I

**질문:** `Policy.read_watch_paths`(§15 — 열람 사실이 중요한 소수 inode 를 감시 목록에
올린다)를 넣을 수 있는가. 읽기를 보려면 읽기 열기가 앞문(`FMODE_WRITE`)을 그냥
빠져나가지 못한다. 3차가 비용의 90% 로 짚은 cgroup 조회까지 가느냐가 관건이라고

| | 읽기 열기에서 | 사전 가설 |
|---|---|---|
| R | cgroup → 태그 → 영장 → 감시 목록 | 읽기마다 D 의 쓰기 경로만큼 낸다 |
| I | 감시 목록 `(dev, ino)` → 걸리면 cgroup … | **해시 miss 1회라 D 와 거의 같다** |

조건: `--tiers a,d,r,i --workloads w_find,w_untar`, 5회 × 4패스. 커널이
**6.8.0-139** 로 올라 있었다(1~3차는 -138). **3차 ns 와 섞어 비교하지 않는다** —
이 실행 안의 D 대비 차이만 읽는다. 거버너는 고정하지 않았다.

**하네스는 맞게 돌았다.** R · I 모두 `watch_hit` 1~2건 — 카나리아 `/usr/bin/env` 가
걸렸으므로 감시 목록 주입(`st_dev` → 커널 `s_dev` 인코딩 변환 포함)이 맞다.
`w_untar` 에서 D · R · I 모두 `tag_hit=40,235`.

#### 마이크로 — 가설이 틀렸다. I 도 R 만큼 비싸다

| | I | −32 | 40,806 | −0.15% | 64-127 |

- ~~**순서는 차이를 못 만든다.**~~ R − I = 22ns 로, 이 실행의 근사 오차(`w_untar` I 가

#### 원인 가설 — 비용은 순서가 아니라 "어떻게 읽나"에 있다 (미측정)

150ns 는 그것치고 크다. 첫 구현에 원인이 있을 가능성이 높다.

- 대안 가설은 `i_ino` 쪽 캐시 미스다. 둘 중 무엇인지는 아직 모른다.

**다음 측정:** I2 = I 와 같은 순서, 직접 load, `f_inode` 1회. I2 ≈ D 면 "순서가 아니라
읽는 방법"이 확정되고 `read_watch_paths` 는 그 방식으로 넣는다. 그래도 비싸면
해시를 빼고 inode 에 표식을 다는 `BPF_MAP_TYPE_INODE_STORAGE` 를 잰다.

### 5차 실행 (2026-09-22, `out/20260922-234417`) — I2 · B 포함

**질문:** 4차에서 I 가 ~150ns 를 낸 원인이 **순서가 아니라 읽는 방법**인가.
I2 = I 와 같은 순서에, `(dev, ino)` 를 `BPF_CORE_READ`(포인터 한 단계마다
`bpf_probe_read_kernel` 헬퍼, I 에서 5회) 대신 BTF 포인터 직접 load 로, `f_inode` 1회.
앞문(`f_mode`)은 D · R · I 와 같게 둬서 차이가 감시 경로에서만 나오게 했다.

조건: `--tiers a,b,d,r,i,i2 --workloads w_find,w_untar`, 5회 × 4패스, 커널 -139.
**거버너 고정 여부는 기록이 없다** — `env.txt` 가 그걸 적지 않았다(아래 하네스 수정).

**하네스는 맞게 돌았다.** I2 의 직접 load 가 verifier 를 통과했다. 네 티어 모두
`watch_hit` 1~2건 — 직접 load 로 만든 키도 맞다. B 가 있어 검산 절이 나왔다.

**이 실행은 노이즈가 작다.** 쓰기 지배 `w_untar` 에서 R · I · I2 가 D 와 **1~3ns**
차이다(4차는 −32ns). 읽기 감시 코드가 거의 안 도는 워크로드라 이 폭이 곧 근사 오차다.

#### 마이크로 — 헬퍼가 주범이었다

`w_find`(읽기 지배), D 대비:

- **헬퍼가 I 비용의 70% 다** (58 / 82ns). 4차의 가설이 맞았다.
- **순서도 차이를 만든다** (R − I = 70ns). 4차의 "순서 무관"은 노이즈에 묻힌 판정이었다.

- **절대 수준:** 모든 읽기가 영장 세션인 최악 조건에서 D(+0.36%) + I2(+0.57%)
  ≈ 0.93%. ~~읽기 감시를 켜도 1% 미만이다.~~ **→ 6차에서 정정:** 같은 I2 가 6차에서
  +1.78%(전체 ≈ 2.0%). 크기는 기계 상태에 따라 2~3배 흔들린다. 실행 한 번으로 적은 결론이었다.
- I2 는 감시 목록을 cgroup 보다 먼저 보므로 이 비용은 **무영장 세션의 읽기에도 똑같이
  붙는다.** 발견 1(E ≈ D)과 같은 이유로 "무영장이면 싸다"를 쓰지 않는다.

**실행을 섞지 말 것 — 다시.** 같은 코드인 I 가 4차 +147ns, 5차 +82ns 다. 5차 안의
비교만 결론이다.

#### 매크로 — 쓸 수 없지만, 검산이 처음으로 제 일을 했다

`w_find` A sd 0.329s(4차 0.210s), 노이즈 바닥 ±16.3%. 거버너가 고정되지 않은 것으로 보인다.

표는 D 를 **+27.5% "±27.0% 초과"(유의)** 로 찍었다. 검산 절이 같은 줄을

똑같은 인공물(`w_untar` I +4.0% 유의)이 판정 없이 남았다 — **B 없이 돌리면 이렇게 된다는

### 6차 실행 (2026-09-23, `out/20260923-005559`) — 전 티어 · 전 워크로드, 거버너 고정

조건: 8티어 × 4워크로드, 5회 × 4패스, `governor 8 performance`(기록됨).

**재현된 것 — 결정은 유지된다.** 읽기가 있는 세 워크로드(`w_build` · `w_find` · `w_git`)
모두에서 **R > I > I2**, 5차와 같은 순위다. 헬퍼 몫(I − I2)도 여전히 크다(`w_find` 78ns).
**`read_watch_paths` 는 I2 방식으로 넣는다 — 바뀌지 않는다.**

**재현되지 않은 것 — 크기.** `w_find` D 대비:

| | 5차 | 6차 |
|---|---|---|
| R | +152ns (+3.6%) | +209ns (+4.9%) |
| I | +82ns (+2.0%) | +154ns (+3.6%) |
| I2 | +24ns (+0.57%) | **+76ns (+1.78%)** |

검산 기준 I2 전체 예상 Δ ≈ **2.0%**. `w_untar` D 도 162ns(+0.73%)로 3차(77ns)의 두 배다.
**정정: 읽기 감시 포함 최악 ≈ 0.9~2.0%, S1 D 단독 0.36~0.73% — 기계 상태에 따라.**
어느 쪽이든 판정 기준(한 자릿수 %)을 넉넉히 통과한다.

**원인 — 마이크로 슬롯마다 기계 속도가 달랐다.** 같은 워크로드의 처리 속도가 티어
슬롯마다 크게 갈린다(`w_find` 초당 열기 C 284k · D 231k · I2 173k, `w_build` C 25k ·
D 10.8k). 훅 비용(21만 × 200ns ≈ 45ms)으로는 설명되지 않는다 — 기계가 느렸다.

- **마이크로는 섞지 않는다.** 매크로는 패스마다 `shuf` 하지만 마이크로는 `b → … → i2`
  고정 순서 1회다. 2차 매크로가 겪은 것과 같은 결함이다.
- **거버너 고정으로는 부족했다.** `performance` 인데도 `w_build` 매크로 sd ≈ 1.0s(평균 3.4s),
  두 모드가 그대로다. 노트북 CPU(i7-1165G7)의 터보 예산 · 발열 제한은 거버너와 별개다.
  3~5차에 적은 "거버너만 고정하면 된다"는 틀렸다.
- 그래서 **발견 1(E ≈ D)도 이 실행에서는 판별되지 않는다** — `w_untar` E 80ns · D 162ns
  인데 D 슬롯이 E 슬롯보다 20% 느린 기계에서 돌았다. 3차의 결론을 뒤집는 근거로 쓰지 않는다.

#### 여기서 닫는다

읽기 감시 측정(4~6차)은 이것으로 닫는다. 질문은 "켜도 한 자릿수 % 안인가"였고 답은
세 실행 모두 예다. 그 뒤로 쫓은 것은 결정을 바꾸지 않는 수십 ns 의 크기였고, 잴 때마다
새 오차 원인이 나왔다. **판정 기준보다 두 자릿수 작은 차이를 노트북에서 재려 한 것이
곁가지가 길어진 이유다.**

**알려진 한계 (고치지 않고 남긴다):** 마이크로 단계 미셔플 · 터보 미고정 · 슬롯별 처리
속도 편차 미경고. ns 단위 크기가 다시 판단 근거가 되는 시점(예: 커널 7.0 · Rocky 9 검증)에
고친다. 그 전까지 이 하네스의 ns 는 **같은 실행 안의 순위**로만 읽는다.

## S2 — 태그 두 겹이 프로세스 트리를 따라가는가 (§04)

**질문:** `sudo`·`su`·`nohup`·백그라운드를 거쳐도 표식이 떨어지지 않는가.
**떨어지면 이 제품은 그냥 또 하나의 셸 래퍼다.**

### 설계 — 두 겹을 따로 기록한다

```
1차  session-N.scope 의 cgroup id → warrant id       (해시맵)
2차  fork 시 부모의 유효 태그를 자식 task_storage 로 복사
```

`wb_rec` 에 `warrant_cg` 와 `warrant_task` 를 **따로** 담는다. "태그가 붙었다"
하나만 보면 `systemd-run --scope`(2차에 걸림)와 `nohup`(1차에 걸림)이 구분되지
않는다 — 그러면 §04 표의 'cgroup' 열과 'fork 체인' 열을 각각 검증할 수 없고,
**2차 방어선이 실제로 일하고 있는지 증명할 방법이 사라진다.**

2차 전파의 핵심은 이 한 줄이다:

```c
__u64 w = wb_tag_by_task(parent);       // 2차 우선
if (!w) w = wb_tag_by_cgroup(parent);   // 없으면 1차에서 승계
```

부모가 cgroup으로만 태그돼 있어도 자식에게는 task_storage로 심는다. 그래야
자식이 나중에 cgroup을 벗어나도 표식이 남는다.

맵은 `/sys/fs/bpf/warrant_bypass` 에 pin한다 — bats 케이스가 각각 별도
프로세스라서다. 제품도 같은 이유로 pin한다(warrantd 재시작 중 태깅 공백 방지).

### 결과 (2026-09-03) — 17케이스 중 8 통과 · 9 skip · **0 실패**

| 세션에서 하는 행위 | cg_tag | task_tag | 문서 예상 | |
|---|---|---|---|---|
| `nohup` · `setsid` · `&` | 1 | 1 | 유지 | ✓ |
| `sudo` · `su` (uid→65534) | 1 | 1 | 유지 | ✓ |
| **`systemd-run --scope`** | **0** | **1** | **2차 방어선** | ✓ |
| `systemd-run` (기본) | 0 | 0 | 끊김 | ✓ |
| `docker exec` | 0 | 0 | 끊김 | ✓ |
| `at` · `crontab` | — | — | 끊김 | skip (atd 없음) |

**§04 표가 커널 6.8.0에서 참이다.**

### 얻은 것

1. **제품의 성립 조건이 실물로 확인됐다.** 표식이 `sudo`·`su`·`nohup`·`setsid`·`&`
   를 전부 통과한다. uid가 바뀌어도 유지된다.
2. **`systemd-run --scope` 의 `cg_tag=0 task_tag=1` 이 S2에서 가장 값진 한 줄이다.**
   cgroup은 갈아탔는데 fork 체인이 살아 표식이 남았다 — **2차 방어선의 존재
   이유가 설계 주장이 아니라 측정값이 됐다. 1차만 있었으면 여기서 뚫린다.**
3. 문서가 인정한 위임 경로가 문서대로 끊긴다. 예상된 결과이고 이것도 검증된 사실이다.

### 한계 — 흐리지 말 것

- **아직 진짜 세션이 아니다.** bats 자신의 cgroup을 태그했다. `session-N.scope` 와
  성질은 같지만, **S3(PAM 타이밍) 뒤에 진짜 세션으로 재확인해야 한다.**
  그때 `helpers.bash` 만 갈아끼우고 케이스는 손대지 않는다.
- **"끊긴다"는 검증했고 "막는다"는 아직이다.** 위임 경로의 진짜 방어선
  (실행 화이트리스트 · AF_UNIX `sun_path` 차단 · spool 쓰기 차단)은 셋 다
  미구현이라 skip이다.
- §18이 인정한 네 구멍(만료 전 열어둔 fd · connect 없는 UDP · 데몬 위임 ·
  `kubectl exec`)은 **skip 사유를 명시해 실패 테스트로 커밋**돼 있다.
  "알고 있으나 막지 못한다"와 "모른다"는 다르게 취급된다.
- **증거 파일이 리포에 없다.** `sudo make test` 는 돌았지만 `bench/bypass/out/` 이
  비어 있다. 심사에서 "돌려봤다"와 "출력이 리포에 있다"는 다르다 — 재실행해서
  커밋할 것.

## S3 — PAM 스택에서 session scope 가 확정되는 타이밍

**질문:** `pam_warrant.so` 가 실행되는 그 순간에 `session-N.scope` 가 이미 있는가.
**실패하면:** 태깅 공백이 생긴다. warrantd 가 cgroup 트리를 순회하거나 logind 의
D-Bus `SessionNew` 를 구독해야 하고, `pam/` 와 `agent/internal/pamsock` 설계가
통째로 바뀐다.

§11 T1 이 "`pam_systemd.so` 뒤에 놓으면 있다"고 적어놨지만 **검증된 적 없는
가정**이었다.

### 설계 — 경로를 두 가지로 구해 나란히 적는다

`pamprobe.c` 는 아무것도 막지 않는다. `open_session`·`close_session`·`acct_mgmt`
마다 한 줄 기록하고 `PAM_SUCCESS` 로 끝난다. sshd 주소 공간 규칙을 지킨다 —
malloc 없음, 고정 버퍼, 폴링 상한 200ms, 모든 실패 경로가 `PAM_SUCCESS`.

| | 무엇 | 왜 |
|---|---|---|
| `proc_cgroup` | `/proc/self/cgroup` | logind 가 `CreateSession` 때 호출자를 scope 로 옮긴다 — sshd 자신이 이관됐나 |
| `scope` | `XDG_SESSION_ID` 로 조립한 경로 | **제품이 실제로 쓸 방법** |
| `match` | 둘이 같은가 | 어긋나면 제품이 `/proc/self/cgroup` 을 읽으면 안 된다는 근거 |

`present_t0` 이 핵심 답이고, `no` 면 상한까지 폴링해 `waited_us` 에 공백을 남긴다.

### 두 번 헛돌았다 — 세션이 안 만들어졌다

1차(2026-09-07)·2차(2026-09-08 오전) 8건 전부 `xdg_session_id=-` 였다.
`proc_cgroup` 이 이렇게 찍혔다:

```
/user.slice/user-1000.slice/user@1000.service/app.slice/
  app-org.gnome.Terminal.slice/vte-spawn-5ab5fe72-….scope
```

**GNOME 터미널 scope 다. `session-N.scope` 가 아니다. 새 세션이 아예 안
만들어졌다.**

원인: **`pam_systemd.so` 는 호출한 프로세스가 이미 사용자 세션 안에 있으면 세션
생성을 건너뛴다.** 데스크톱 터미널에서 `pamtester` 나 `su` 를 돌리면 그 프로세스는
`user@1000.service` 아래라 logind 가 아무것도 안 만든다.

**절차 설계의 오류였다.** README 에 "2단계(`/etc/pam.d/su`)에서 진짜
`session-N.scope` 가 생기니 여기서 답이 나온다"고 적어놨는데, **`pam_systemd.so` 가
스택에 있는 것과 그게 실제로 세션을 만드는 것을 같게 놓은 것**이다. 위험 낮은
단계로 답의 80%를 얻겠다던 계획이 0% 였다.

`report.py` 도 같은 이유로 틀린 진단을 냈다 — "삽입 위치가 `pam_systemd.so` 보다
앞이다, 내려라". **위치는 맞았다.** 없는 문제를 쫓게 만드는 메시지다.
→ `proc_cgroup` 의 `user@N.service` 로 **"세션이 안 만들어졌다"와 "위치가 틀렸다"를
가르도록** 고쳤고, 전자는 판정 대상에서 아예 제외한다(실패가 아니라 구조적으로
답할 수 없는 행이라, 섞어 세면 `3/11` 로 보여 통과가 안 보인다).

**프로브 설계가 이걸 구했다.** `proc_cgroup` 을 같이 안 찍었으면 "`XDG_SESSION_ID`
가 왜 비지?"에서 막혔다. 값 하나가 원인 규명을 대신했다.

### 3차 — 세션 밖에서 부르니 만들어졌다

```sh
systemd-run --scope --slice=system.slice --quiet pamtester -v warrant-probe $USER open_session
```

`system.slice` 로 빠져나가면 "이미 세션 안"이 아니게 되므로 logind 가 세션을
만든다. 3/3 `present_t0=yes`.

**여기서 예상 못 한 수확이 나왔다.** 3회 모두 `session-4.scope` 인데 cgroup id 가
다르다:

```
session-4.scope  →  cgid 13299, 13408, 13517
```

**`XDG_SESSION_ID` 는 재사용된다. cgroup id(inode)는 아니다.** 세션이 끝나면
logind 가 번호를 반납하고 다음 세션이 같은 번호를 다시 받는데, cgroup 은 새로
만들어지니 inode 가 다르다.

**영장을 세션 번호에 걸었다면 다음 세션이 남의 영장을 물려받는다.** 만료 전에
로그아웃한 사람의 영장을 같은 번호를 받은 다른 세션이 그대로 쓰게 된다.
**§11 T1 이 cgroup id 를 키로 쓰는 설계의 직접 증거**이고, 재려던 게 아니라
로그에 딸려 나온 것이다. `report.py` 가 이제 이 패턴을 자동으로 찍는다.

### 4차 — sshd. 최종 답 (2026-09-08, `out/20260908-230244`)

`/etc/pam.d/sshd` 에 삽입하고 `ssh localhost` 11회. 세션 14~24.

| | 결과 |
|---|---|
| `XDG_SESSION_ID` 가 있다 | **11/11** |
| `session-N.scope` 가 이미 있다 | **11/11** ← §11 T1 의 가정 |
| `/proc/self/cgroup` 과 일치 | **11/11** |
| `waited_us` | **전건 0** — 폴링이 한 번도 안 돌았다 |

**S3 통과. 태깅 공백이 없다.**

- **설계가 안 바뀐다.** `pam_warrant.so` 는 `XDG_SESSION_ID` → 경로 조립 → `stat`
  로 끝난다. warrantd 의 cgroup 트리 순회도 logind D-Bus 구독도 필요 없다.
- **(§11 T4) `close_session` 에서 scope 가 아직 살아 있다 (11/11).**
  `cgroup_warrant` 엔트리 정리를 여기에 걸 수 있다. 다만 `nohup` 으로 살아남은
  프로세스가 있으므로 정리 정책은 별도 판단이다.
- `ssh localhost` 도 원격 접속과 경로가 완전히 같다 — sshd → PAM 스택 →
  `pam_systemd.so` → `session-N.scope`. 다른 건 `rhost` 뿐이고 측정 대상이 아니다.
  그리고 **깨진 걸 알아차리는 창구와 고치는 창구가 같은 자리에 있어서** 원격보다
  안전하다.

### 안전 절차 — 이 실험만 기계를 잠글 수 있다

`/etc/pam.d/sshd` 가 망가지면 SSH 로 다시 못 들어온다. 기계가 멈추는 건 아니다 —
열린 세션도 서비스도 콘솔 로그인(`/etc/pam.d/login`)도 `sudo`(`/etc/pam.d/sudo`)도
멀쩡하다. **복구 경로가 하나 줄어드는 것**이 위험이다.

그래서 단계를 올려가며 확인했다:

| | | 위험 | 알 수 있는 것 |
|---|---|---|---|
| 1 | `pamtester` 전용 서비스 | 0 | 모듈이 세그폴트하지 않는다 |
| 1.5 | `system.slice` 에서 `pamtester` | 0 | **판정 가능** |
| 2 | `/etc/pam.d/su` | 낮음 | `su` 경로에서도 안 죽는다 |
| 3 | `/etc/pam.d/sshd` | 여기만 | **최종 답** |

넣는 줄은 `session optional …` 이라 모듈이 실패를 반환해도 로그인이 진행되고,
`.so` 를 못 읽어도 PAM 이 넘어간다. 실제 위험은 **세그폴트와 무한 대기 둘뿐**이고
1·2단계가 그걸 걸러낸다. 원본은 `.warrant-bak` 로 백업되고 `make disable` 이
복원한다.
